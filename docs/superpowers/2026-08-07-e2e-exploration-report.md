# Отчёт разведочного E2E-прогона

**Дата:** 2026-08-07
**Сборка:** production (`vite preview`), Chromium desktop 1440×900 и Pixel 7 (Chromium mobile)
**Тест:** `tests/e2e/exploration.spec.ts` (тег `@exploration`, 4 сценария × 2 проекта = 8 прогонов, все зелёные)

## Дефекты

### D-1. Пользовательский строй нельзя выбрать в тюнере повторно — селектор строит список только из пресетов

- **Экран:** Тюнер (селектор строя в шапке блока тюнера) + Настройки (список сохранённых строёв)
- **Вьюпорт:** оба
- **Шаги:**
  1. Открыть Настройки → «Пользовательские строи» → «Создать строй».
  2. Ввести имя «Мой тестовый строй QA», оставить ноты по умолчанию (E2 A2 D3 G3 B3 E4), нажать «Сохранить строй».
  3. Нажать «Сохранить и закрыть».
  4. Посмотреть на `<select>` строя на экране тюнера.
- **Ожидалось:** новый строй появляется как выбранный пункт в выпадающем списке; после переключения на другой пресет пользователь может выбрать свой строй обратно через тот же селектор.
- **Фактически:** `<select>` показывает 17 опций — ровно список `TUNING_PRESETS`, без созданного строя. При этом заголовок экрана (`h2`) и подзаголовок в шапке приложения корректно показывают «Мой тестовый строй QA» (реальное состояние `currentTuning` в React верное), а `<select>.value` возвращает `"standard-e"` (браузер откатывается на первую опцию, потому что `value={tuning.id}` не совпадает ни с одной `<option>`). Получается расхождение на экране: заголовок говорит «активен мой строй», а выпадающий список показывает «Standard E (EADGBE)».
  Скриншот-доказательство: `test-results/exploration--exploration-г-a5f98-ий-строй-в-селекторе-тюнера-chromium-desktop/chromium-desktop-hypothesis1-after-custom-tuning.png`.
  Полный дамп списка опций записан в консоли теста (блок «ГИПОТЕЗА 1»): 17 значений `standard-e … ukulele-low-g`, кастомный строй отсутствует.
  Дополнительно: в модалке настроек у сохранённых строёв (`SettingsModal.tsx:356-384`) есть только кнопка удаления (`Trash2`, `SettingsModal.tsx:374-380`) — обработчика «применить/выбрать» нет. Единственный момент, когда кастомный строй становится активным — сразу после его создания (`onCustomTuningCreated` в `App.tsx:317`). Если пользователь после этого переключится на пресет (через тот же `<select>`, который его прекрасно видит) — вернуться к своему строю через UI тюнера или настроек уже нельзя. Он останется доступен только случайно — если `gt_tuning` в `localStorage` всё ещё указывает на него при следующей перезагрузке страницы (`App.tsx:17-25` восстанавливает и пресеты, и кастомные строи при монтировании).
- **Причина в коде:**
  - `src/features/tuner/TunerScreen.tsx:307-309` — `<option>` строится только из `TUNING_PRESETS.map(...)`, без `loadSavedCustomTunings()`.
  - `src/App.tsx:17-25` — при восстановлении из `localStorage` `App` мержит `TUNING_PRESETS` и `loadSavedCustomTunings()`, то есть знает о кастомных строях; это не используется в `TunerScreen`.
  - `src/features/settings/SettingsModal.tsx:354-384` — список сохранённых строёв не имеет действия «выбрать», только «удалить».
- **Приоритет:** важный. Приложение не падает и не теряет данные (строй сохраняется в `localStorage`), но заявленная функция «пользовательские строи» по факту работает только один раз за сессию создания — сразу после сохранения. Повторно выбрать сохранённый строй пользователь не может никаким способом через интерфейс.
- **Решение заказчика (2026-08-07): в бэклог.** Требуется продуктовое решение: добавлять ли кастомные строи в `<select>` тюнера, или делать отдельный UI выбора в настройках с кнопкой «Применить». В сьюте заведён `test.fixme('сохранённый пользовательский строй можно выбрать повторно')` в `tests/e2e/settings.spec.ts` — он описывает желаемое поведение и включится после исправления.

### D-2. Экспорт SVG с экрана «Гриф» отдаёт иконку тюнера 15×15, а не схему грифа

- **Экран:** Гриф
- **Вьюпорт:** оба (идентичное поведение)
- **Шаги:**
  1. Перейти на экран «Гриф».
  2. Нажать кнопку с иконкой скачивания (title=«Экспортировать SVG»).
  3. Открыть скачанный файл `fretboard-explore-A.svg`.
- **Ожидалось:** SVG-файл со схемой грифа (лады, струны, подсвеченные ноты), пригодный для печати/шаринга.
- **Фактически:** файл размером **371 байт**. Первые 200 символов содержимого:
  ```
  <svg xmlns="http://www.w3.org/2000/svg" width="15" height="15" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide lucid
  ```
  `viewBox="0 0 24 24"` и `width="15" height="15"` однозначно указывают на иконку lucide (набор иконок в проекте рисуется как 24×24 vector, масштабируемый под `size` пропом), а не на диаграмму грифа. На странице «Гриф» в момент экспорта в DOM присутствует 17 элементов `<svg>` (записано в логе теста, блок «ГИПОТЕЗА 2»); `document.querySelector('svg')` берёт первый попавшийся — это иконка `Activity` (пункт «Тюнер») из **десктопной шапки навигации** (`size={15}`, что совпадает с зафиксированными `width="15" height="15"`). Она находится в DOM даже на мобильном вьюпорте (там `desktop-nav` скрыт через CSS `display:none`, но не удалён из дерева), поэтому баг одинаково воспроизводится на обоих проектах.
- **Причина в коде:** `src/features/fretboard/FretboardScreen.tsx:83` — `document.querySelector('svg')` без какого-либо уточняющего селектора/рефа на сам `<FretboardSVG>` (рендерится этим же компонентом на `FretboardScreen.tsx:401-411`).
- **Приоритет:** важный. Кнопка не выдаёт ошибку и не ломает остальной интерфейс — просто молча скачивает бесполезный файл. Функция экспорта полностью нерабочая для заявленной цели (FR-FB-19 — экспорт схемы грифа).
- **Решение заказчика (2026-08-07): чинить сейчас.** Исправление входит в объём Task 8: `ref` на корневой `<svg>` в `FretboardSVG.tsx` (React 19 принимает `ref` обычным пропом) вместо `document.querySelector('svg')`. Тест `экспорт скачивает схему грифа, а не иконку` в `tests/e2e/fretboard.spec.ts` написан под корректное поведение и обязан проходить.

### D-3. Несовпадение подписи вкладки «Тренажёр слуха» между десктопной и мобильной навигацией

- **Экран:** Тренажёр слуха (навигация к нему)
- **Вьюпорт:** мобильный (Pixel 7); на десктопе не воспроизводится
- **Шаги:** Открыть приложение на мобильном вьюпорте → попытаться найти в нижнем таб-баре кнопку с текстом «Тренажер».
- **Ожидалось:** подпись вкладки одинакова на обоих вьюпортах (как у остальных четырёх вкладок: Тюнер/Гриф/Аккорд/Ритм).
- **Фактически:** десктопная навигация подписывает вкладку «Тренажер» (`App.tsx:132`), а нижний таб-бар на мобильном — «Слух» (`App.tsx:301`). Оба ведут на один и тот же `activeTab === 'ear-training'`, разница чисто текстовая. Наш собственный разведочный проход (`exploration.spec.ts`, сценарий «обход всех экранов») это поймал автоматически: на прогоне `chromium-mobile` он записал в наблюдения `Не удалось найти видимую кнопку навигации: Тренажер` и пропустил скриншот этого экрана — доказательство, что locator по регулярке `/Тренажер/` не находит видимую кнопку на мобильном вьюпорте.
- **Причина в коде:** `src/App.tsx:132` (`<Sparkles size={15} /> Тренажер` — десктопный `<nav className="desktop-nav">`) против `src/App.tsx:301` (`<span>Слух</span>` — `<nav className="mobile-bottom-nav">`).
- **Приоритет:** косметический для конечного пользователя (кнопка рабочая, просто разное слово), но **важный для дизайна тестового сьюта** — см. раздел «Влияние на сьют».
- **Решение заказчика (2026-08-07): оставить как есть.** Короткое слово «Слух» лучше помещается в узком таб-баре, а на сьют расхождение не влияет: навигация в тестах идёт через `nav-desktop-ear-training` / `nav-mobile-ear-training`, а не по тексту кнопки. Продуктовый код не меняется.

### D-4. Сброс на экране проверки аккорда не приостанавливает живую подписку на микрофон

Найдено не разведкой, а при написании сценариев (Task 9), поэтому нумерация продолжена.

- **Экран:** Проверка аккорда, режим A (перебор)
- **Шаги:** включить микрофон, дать струне прозвучать до статуса «В строе», затем нажать «Сбросить», не выключая микрофон.
- **Ожидалось:** статусы струн возвращаются в «Ожидание» и остаются там до следующего звука.
- **Фактически:** подписка `sharedAudioEngine.subscribe(...)` в `ChordCheckScreen.tsx` не имеет защиты по `isListening` и продолжает обновлять `stringStatuses` во время сброса. `AnalyserNode` после пропадания звука ещё около 100–250 мс отдаёт валидные оценки с высокой чистотой, пока промывается его окно анализа. Попавшая в это окно оценка перезаписывает только что сброшенный статус.
- **Причина в коде:** `src/features/chord-check/ChordCheckScreen.tsx:54-65` — обработчик подписки; `src/features/chord-check/ChordCheckScreen.tsx:136-141` — `resetAnalysis` не трогает подписку.
- **Приоритет:** косметический. Состояние самокорректируется: следующий же тик с тишиной возвращает статус в «Ожидание». Пользователь может увидеть кратковременное мигание статуса после нажатия «Сбросить».
- **Как обнаружено:** тест «сброс возвращает статусы в ожидание» падал в 15–20% одиночных прогонов. Причина установлена инструментированием, инструментирование удалено до коммита.
- **Решение:** в бэклог. В сьюте тест выключает микрофон перед сбросом — это сужает сценарий (сброс при живом микрофоне не покрыт), и данный пункт фиксирует непокрытое поведение.

### D-5. Манифест PWA не подключён к странице, иконки манифеста отсутствуют

Найдено при написании сценариев PWA (Task 12), а не разведкой: разведка проверяла поведение экранов, а не установочные метаданные.

- **Экран:** всё приложение
- **Шаги:** открыть приложение, посмотреть `<head>` документа; запросить файлы иконок, перечисленные в `public/manifest.json`.
- **Ожидалось:** браузер обнаруживает манифест и предлагает установку; иконки отдаются с кодом 200.
- **Фактически:**
  - в `index.html` нет `<link rel="manifest">` — есть только инлайновый favicon-эмодзи и ссылки на шрифты, поэтому `public/manifest.json` браузером не читается вовсе;
  - `public/` содержит `favicon.svg`, `icons.svg`, `manifest.json`, `qrCode.png`, `sw.js`; файлов `icon-192.png` и `icon-512.png`, на которые ссылается манифест, не существует.
- **Следствие:** приложение **нельзя установить** как PWA — нет иконки на домашнем экране, отдельного окна и splash-screen. При этом офлайн-режим работает: Service Worker регистрируется из `main.tsx` и кэширует сборку, тест офлайна прошёл 12 прогонов из 12 с проверкой реального отрисованного контента.
- **Расхождение с документацией:** README заявляет «PWA Offline Ready» и «Web App Manifest», `_worklog/PROGRESS.md` — настроенный PWA. Заявление про манифест было неверным.
- **Причина в коде:** `index.html` — отсутствует `<link rel="manifest">`; `public/manifest.json:11-24` — ссылки на несуществующие `icon-192.png` и `icon-512.png`.
- **Приоритет:** важный. Половина заявленной функциональности PWA не работает.
- **Решение заказчика (2026-08-08): починить полностью.** В `index.html` добавляется `<link rel="manifest">`, генерируются настоящие PNG-иконки 192×192 и 512×512 на фоне `#0B0A1C` с логотипом из `favicon.svg`, с учётом безопасной зоны для `purpose: "any maskable"`. Тесты `pwa.spec.ts` не менялись — они были верны и именно они вскрыли дефект.

## Влияние на сьют

- **Навигация (Task 5)**: расхождение подписей (D-3) на сьют не влияет — навигация идёт через `data-testid` (`nav-desktop-ear-training` / `nav-mobile-ear-training`), а не по тексту кнопки. Именно поэтому контракт testid'ов разделяет десктопную и мобильную навигацию: обе панели присутствуют в DOM одновременно и различаются только стилями, так что текстовый локатор здесь ненадёжен в принципе, независимо от D-3.
- **Сценарии тюнера (Task 6) и настроек (Task 7)**: сценарий «пользователь создаёт кастомный строй и тюнер её использует» нельзя писать как happy path с проверкой присутствия строя в `<select>` — по факту его там нет (D-1). Сценарий должен либо: (а) фиксировать текущее (дефектное) поведение как есть — строй активен сразу после создания, но не выбираем повторно через селектор; либо (б) быть помечен `test.fixme` со ссылкой на D-1, если фикс уйдёт в бэклог. Также любые сценарии, которые переключают строй через `<select>` **после** создания кастомного, должны учитывать, что `<select>.value` в этот момент равен `"standard-e"`, а не id кастомного строя — это может маскировать реальный баг переключения строя, если тест доверяет отображаемому значению селектора вместо факта смены струн/заголовка.
- **Сценарии грифа (Task 8)**: поскольку D-2 решено чинить в рамках Task 8, сценарий «экспорт SVG» пишется под корректное поведение — проверяет содержимое скачанного файла (размер и отсутствие `viewBox="0 0 24 24"`) и обязан проходить после исправления. Задача Task 8 включает и продуктовый фикс, и тест на него.
- **Общая инфраструктура (пригодится для Task 14 / любых будущих точечных прогонов)**: в установленной версии Playwright (`1.62.1`) конфигурационный `grepInvert` в `playwright.config.ts` применяется на этапе построения project suite **до** учёта CLI-флагов `--grep`/`--grep-invert` — они не переопределяют, а лишь дополнительно фильтруют уже отфильтрованный набор. Из-за этого документированная в задаче команда `npm run test:e2e -- --grep @exploration` возвращает `Error: No tests found` и не запускает `exploration.spec.ts` вовсе. Разведочный прогон в этом отчёте был выполнен через временный локальный конфиг-оверрайд (`playwright.exploration.local.config.ts`, наследующий `playwright.config.ts` с `grepInvert: undefined`), который не коммитился и был удалён после использования. Рекомендация на будущее: либо не полагаться на `--grep` для обхода `grepInvert` в этой версии Playwright, либо описать альтернативный способ (отдельный npm-скрипт с отдельным конфигом, либо `test.skip`/условие на env-переменную вместо `grepInvert`) — иначе Task 14 («Полный прогон и документация») рискует наткнуться на ту же проблему при попытке прогнать `@exploration` отдельно от основного сьюта.
